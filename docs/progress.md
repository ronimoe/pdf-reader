## Hotfix: PDFKit background-queue crash (branch `fix-pdfkit-background-calls`)

**What you saw:** repeated "Lectern quit unexpectedly" dialogs, about 12 between 18:10 and 18:13.

**Cause.** On macOS 26, PDFKit runs private, Vision-based page analysis on a background queue whenever pages scroll into view: form-field detection, OCR and table detection. It adds the detected fields as annotations, and in doing so reads `PDFView.document`. `ReaderPDFView` overrode `document` with a main-actor observer, so Swift 6's isolation check trapped on PDFKit's queue.

**Fix**
- `document` is no longer overridden. Callers use `ReaderPDFView.show(_:)`, which resets the view synchronously.
- PDFKit's private `formDetectionEnabled` and `documentAnalysisEnabled` switches are turned off on every `ReaderPDFView`, only where they exist. This fits the "no AI features" principle and the rule that a document is never changed behind the reader's back.
- A test fails if a future PDFKit renames these switches.

**Verified**
- Regression tests read `document` from a background thread and check that both switches are off.
- The built app was opened on all 8 real-world PDFs, including the IRS forms, with no new crash reports.

**Also seen in the crash reports, and expected:** 3 deliberate crash probes from the M0/M1 reviews (15:12, 15:24), and 1 test-host crash from an M0b spike (15:53).

## M7: Annotations in encrypted PDFs (branch `m7-encrypted-save`, PR #18)

You chose on 2026-10-30 to support this before 1.0. It amends B6: the owner password now also allows annotating and saving.

**Landed**
- **Supported encryption:** the Standard security handler.
  - R2 and R3 use RC4.
  - R4 uses `/V2`, `/AESV2` or `/Identity` crypt filters, with `StmF` and `StrF` allowed to differ, and supports `EncryptMetadata false`.
  - R6 uses AES-256.
  - The file keeps its own encryption. `/Encrypt` and `/ID` are unchanged, and the original bytes remain a prefix of the saved file.
- **Passwords:** PDFSave authenticates the password itself: the session password as the user password, then as the owner password, then the empty password. It never writes with a key it hasn't authenticated.
- **Reading:** the parser decrypts strings, streams and object streams, so the matcher and the M6 page filter see real annotations in encrypted files.
- **Writing:** each new or rewritten object is encrypted with its own key. Data from an existing object is decrypted and then re-encrypted, never copied across as ciphertext.
- **Two read-back checks after every save:**
  - `SavedFileCheck`, through PDFSave's own decryption.
  - An independent check in PDFKit, unlocked with the session password, that compares each added or edited annotation's subtype and `/Contents`.
- **Crash journal:** for encrypted documents it is sealed with AES-GCM, under an HKDF key derived from the file key and salted with a digest of `/O` and `/U`. It restores only after the document is unlocked, and a journal that can't be opened is kept.
- **`DocumentKey`:** an encrypted file without `/ID` is now keyed by its `/O` and `/U` digest, so its Keychain entry and journal survive a save.
- **Still refused, with a message:** R5, the public-key handler, custom crypt filters, and any password that can't be authenticated.
- **Unsupported-handler notice:** a file using a handler Lectern can't decrypt now shows a quiet notice when it opens, because PDFKit would show blank pages.
- **Undo after a save:** the writer gets each annotation's net change. Before this, commenting on a saved highlight, saving, undoing both steps and saving again failed. That bug predates M7.
- **Test gate:** `scripts/test.sh` fetches the checksum-pinned downloaded PDFs first. A missing fetched file now fails only its own test cases.

**Oracle:** for every supported variant, the same edits were made on a decrypted twin (`qpdf --decrypt`) and on the encrypted file. Once qpdf decrypted the output, the annotation objects were identical. The output also passed:
- `qpdf --check`;
- MuPDF, pdf.js and PDFKit, each opening it with the password. Poppler was also checked except on the hand-built identity-strings file, which it can't read even unmodified.

PDFSave's file key matched qpdf's for the user and owner passwords of every fixture. Files encrypted by macOS itself (CoreGraphics and PDFKit) are read and saved into.

## After M7: logo licence and a rotation crash (PRs #19, #20)

**PR #19, logo licence:** the logo and app icon are kept out of the GPL (`design/logo/LICENSE.md`), and the app's Acknowledgements say so. The DMG and cask were rebuilt.

**PR #20, a crash closing a window right after rotating:**
- **What happened:** while PR #19 was being checked, two full test runs crashed the test host inside PDFKit, in `SplitView.layoutRotationAndZoomKeepBothPanesPlaces`. The faulting frame was `-[PDFDocumentView layoutDocumentView]`, a null dereference, from the block `-[PDFDocumentView didRotatePageNotification:]` queues on the main queue.
- **Cause, established by experiment:**
  - A page rotation queues one relayout block per view per page. Each block retains PDFKit's inner document view but not the `PDFView`, so if the `PDFView` is freed first, the relayout crashes.
  - Closing the document is harmless while the views stay alive.
  - A rotation on another `PDFDocument`, such as the thumbnail renderer's copy, doesn't reach the view.
- **How the app could hit it:** the queued relayouts normally run within about 3 ms. But AppKit takes events that are already waiting before it drains the main queue, so a ⌘W typed during a slow rotation can free the views first.
- **Fix:** `ReaderPDFView.outliveQueuedPDFKitWork()` keeps a view alive until the main queue has run what is already on it (two hops). It is called when a pane closes, when the document closes and when the window closes.
- **Test:** `SplitView.closingInTheSameTurnAsARotationIsSafe` replays the original test's sequence and frees the window inside an autorelease pool. It crashed with the same stack without the fix.

**Verified:**
- **Before the fix:** the original test crashed within 5 repeats.
- **With the fix:**
  - the original test alone passed 50 repeats in a row;
  - the original and the new test together passed 20 repeats;
  - the full gate results are in PR #20.

**Not verified:** the crash itself in a running copy of the app, from a real ⌘R then ⌘W. That needs a hand check.
